# Retrieval evals as a CI gate

Tests check that code does what it says; evals check that a system that ranks or generates does it well enough, on a labelled set. For retrieval the classic metrics are recall@k (did the right item appear in the top k), MRR (how high the first right item ranks, as 1/rank averaged over questions), and nDCG@k (graded credit that rewards putting right items near the top). A committed baseline turns those numbers into a regression gate: CI fails if a change drops a metric by more than a small tolerance. The offline eval uses the deterministic fake embedder so it is fast and reproducible; a nightly job later runs the same set against the real local embedding model, which costs nothing but a 180 MB download.

## What the numbers show

`evaluate` reports the hybrid metrics overall and per kind, and, next to them, each branch on its own: text-only recall@k and MRR (through the same `text_query` the fusion uses), vector-only recall@k and MRR, and how often the text branch is non-empty. With the lexical `FakeEmbedder` on the committed set (41 items, 31 questions, 18 `exact_name` and 13 `paraphrase`) the baseline is:

| kind | hybrid recall@5 | hybrid MRR | text-only recall@5 | text-only MRR | text branch non-empty |
|---|---|---|---|---|---|
| exact_name | 1.000 | 1.000 | 0.889 | 0.889 | 0.944 |
| paraphrase | 0.731 | 0.673 | 0.731 | 0.554 | 1.000 |
| overall | 0.887 | 0.863 | 0.823 | 0.748 | 0.968 |

The gate commits the three hybrid metrics plus text-only recall and MRR on `exact_name` (0.889 each); the paraphrase text-only numbers, and every vector-only number, are reported but not gated.

Three things are measured here, and only the text-only keys show the second of them.

**Paraphrase questions measure lexical overlap with the body, not paraphrase ability.** The 13 paraphrase questions are title-disjoint: no content word is shared with the relevant title. But the fake embedder is a hashed bag of words, so the vector branch scores on any word shared with the item's body anyway. A paraphrase question that happens to share body words is retrieved, and one that does not is missed; under M1 that was the whole 0.577, and after Task 12 the OR text branch raises both the hybrid and the text-only paraphrase recall@5 to 0.731 for the same reason, matching shared body words. The number is a fact about this embedder's overlap with these bodies, not about how well natural-language questions are handled.

**The OR text branch reaches almost every natural question.** `websearch_to_tsquery` ANDs a question's content words, so under M1 a long natural question rarely matched any item: the text branch was non-empty for only 1 of the 13 paraphrase questions (0.077) and returned a relevant item for the same one (text-only recall@5 0.077). Task 12 joins the stems with OR, so the text branch is now non-empty for all 13 paraphrase questions and text-only paraphrase recall@5 is 0.731. The hybrid paraphrase numbers rise with it (recall@5 0.577 to 0.731, MRR 0.538 to 0.673), and overall hybrid recall@5 goes 0.823 to 0.887 and MRR 0.806 to 0.863. The gated `exact_name` text-only recall@5 and MRR rise from 0.778 to 0.889. Hybrid `exact_name` stays at 1.000: the vector branch drops rows at cosine distance 1 (similarity zero), so the many items that share no word with the query are not candidates and their shared rank cannot hand a decoy a second RRF contribution. The `or` questions show a related trap (they are `exact_name`, not paraphrase): with the OR branch, "NimbusBench or long tool chains" matches both the target and a decoy that shares the common words, and the gate's text-only MRR is what catches a wrong ordering of that list.

**Risk (2), the `english` tokeniser and space-separated names, is measured only through the text-only keys.** Three committed questions use model names in the spelling a person would type: `Llama-3.1-8B` asked as "llama 3.1 8b", `Qwen2.5-VL` asked as "qwen 2.5", and `RAG/agentic` asked as "RAG agentic". The item's `tsvector` splits the hyphen and keeps the slash compound as one token, while the question's terms do not. The OR branch bridges two of them because one shared stem is now enough: "llama 3.1 8b" matches the item's `llama` token, and "ToolBench and AgentBench evaluation suites", which ANDs two names no single item holds (risk (1) again), now matches one of the two benchmarks. Two still miss: "qwen 2.5" shares no stem with `qwen2.5-vl`, and "RAG agentic" shares no stem with the single `rag/agentic` token. Those two misses are why text-only exact-name recall is 0.889 (16 of 18), not 1.000, and the number is committed as the baseline. The hybrid branch still finds both through the lexical vector branch, so hybrid exact-name recall stays 1.000 even though the text branch misses them.

The gate catches a broken text branch because of the branch-only metrics and the decoys, not because the hybrid ranking happens to move. Three decoy questions ("What is it about NimbusBench for me?") put the target below a decoy in the vector branch, so only a working text branch lifts it back to rank 1, and text-only exact-name recall falls to 0 if the branch returns nothing. The decoys work because `FakeEmbedder` counts stop words ("what is it about ... for me") that Postgres' `english` config drops from the tsquery, so they are a property of this embedder, not of the topics. Three further questions pair a decoy with an "or" query so each has a text list of two or more items, which is what makes a worst-first sort drop the text-only MRR. Patching `text_query` to return nothing, to never match, to sort worst-first, or dropping the text list from the fusion each makes `paperwatch eval` exit 1; that is the acceptance test the Task 11 reviews asked for. The old `_check_no_ties` tripwire, which stopped a top k that depended on the order a random `uuid` broke a tie, is gone. The reproducibility guarantee is carried by the unit tests that pin shared ranks and the stable `(source, external_id)` key (`test_shared_ranks_skip_after_a_tie`, `test_equal_distances_share_a_vector_rank`, `test_equal_text_ranks_share_a_rank`, and the key-order tests in `tests/integration/test_hybrid.py`); `tests/integration/test_eval_throwaway.py::test_eval_is_identical_across_fresh_databases` is a check that scores four fresh databases and asserts every metric matches. The eval also reports the informational `fused_ties_in_top_k`, the number of questions whose top k+1 hits hold an equal fused score, so a data edit that creates one, including a tie that straddles the cut, is visible even though the stable key already orders it.

The other retrieval risks (ts_rank normalisation, `ef_search` recall, candidates and `rrf_k`, a calibrated similarity floor) depend on a real embedder and real volume, so they are measured on real data with the local model at the corpus-size checkpoints, not with 41 synthetic items.

The implementation is `evals/retrieval_eval.py` with the labelled set in `evals/data/`, the committed baseline in `evals/baseline.json`, the gate `paperwatch eval` (the `eval` CI job, which runs it in a throwaway database it creates and drops) and the tests in `tests/integration/test_eval_gate.py`, `tests/integration/test_eval_throwaway.py` and `tests/unit/test_retrieval_eval.py`.
