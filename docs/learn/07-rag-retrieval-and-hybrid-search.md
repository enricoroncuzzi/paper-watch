# RAG retrieval and hybrid search

Retrieval-augmented generation answers from text retrieved at question time, so the quality ceiling is set by retrieval, not by the model. Vector search finds meaning ("tools for autonomous coding") but blurs exact names ("SWE-bench", "Qwen3"); keyword search finds exact names but misses paraphrase. Hybrid search runs both and fuses the two ranked lists with Reciprocal Rank Fusion: each item scores the sum of 1/(60 + rank) over the lists it appears in. RRF needs no score calibration between the two systems, which is why it is the standard first fusion method. Filters (tier, profile, date) are applied inside both queries so they shape the candidates, not just the final list. Only admitted items are searchable: candidates and irrelevant items live in the same table without an embedding, and the vector index covers admitted rows only.

## AND, OR and ranking

A full-text query is a boolean expression over word stems. `websearch_to_tsquery` joins every word with AND, which is precise for a name ("SWE-bench Verified") and useless for a paraphrase, where the paper uses other words for most of the question. Joining the stems with OR finds every item sharing any meaningful word, and cover-density ranking (`ts_rank_cd`) puts items matching more of the words, closer together, first. The filtering moves from the query to the ranking, and the fusion with the vector branch decides the rest. Stop words never become terms, so OR does not match "the" everywhere.

OR matching makes equal scores common in both branches: `ts_rank_cd` ties items whose text matches equally well, and the offline `FakeEmbedder` puts many items at the same cosine distance. Each branch therefore returns `(id, score)` rows and a shared `shared_ranks` helper gives equal scores the same rank (competition ranking, 1-2-2-4) before the fusion, so no item gains a rank from its random `uuid`. The stable `(source, external_id)` key then orders equal fused scores for output, and orders a branch list cut at `k`.

One limit is deliberate. On a corpus larger than `candidates`, a tie exactly at the candidate boundary can still change which rows enter a branch, because HNSW returns only its nearest `candidates` rows. Real 384-dimension embeddings make an exact distance tie vanishingly rare; the eval's hashed fake embedder is the case that does tie, and its 41-item corpus is smaller than the 50 candidates, so all rows are returned. A vector row at cosine distance 1 (similarity zero: the query and the item share no direction) is dropped before ranking, because it is not evidence; real English embeddings practically never reach it, but the fake embedder's orthogonal rows do.

The implementation is `src/paperwatch/retrieval/hybrid.py`, run by `paperwatch search QUERY --live` and covered by `tests/integration/test_hybrid.py`, which pins the fusion, the filters, the two rejection paths and the partial-index match.
